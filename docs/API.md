# MetaShop — API Reference

**Public entry point (use this): API Gateway `http://localhost:8080`**

Direct service ports (bypass the gateway; used for service-to-service calls and debugging):
auth-service `http://localhost:8081` · product-service `http://localhost:8082` ·
inventory-service `http://localhost:8083` · cart-service `http://localhost:8084` ·
order-service `http://localhost:8085` · payment-service `http://localhost:8086` ·
notification-service `http://localhost:8087` · discovery-server (Eureka) `http://localhost:8761`
Swagger UI: `/swagger-ui/index.html` · OpenAPI JSON: `/v3/api-docs` (per service)

All services use the `/api/v1/...` base path, and the gateway forwards it unchanged. See
`DECISIONS.md` (D-003, D-041).

**Response shapes.** Two conventions coexist; each service section states which one it uses.

- `auth-service` and `product-service` (the two oldest) wrap **successful** list/collection
  responses in the `ApiResponse` envelope:

  ```json
  { "success": true, "message": "Products fetched successfully", "data": { } }
  ```

- The newer services — `inventory-service`, `cart-service`, `order-service`, `payment-service`,
  `notification-service` — return **plain DTOs** on success (a paged object for lists, the DTO
  itself for detail) and reserve the envelope for errors. That keeps the service-to-service Feign
  clients trivial, and it is the convention new endpoints should follow.

**Errors always use the envelope**, in every service:
`{ "success": false, "message": "...", "data": ... }` with the appropriate HTTP status
(`400`, `404`, `409`, `422`, `500`).

Errors **generated by the gateway itself** (401/403/404/429/503) use the spec §5.3 shape instead:

```json
{ "timestamp": "...", "status": 401, "error": "UNAUTHORIZED", "message": "...",
  "path": "/api/v1/users/me", "traceId": "<correlation id>" }
```

## API Gateway (`:8080`)

Single public entry point. Validates the JWT, propagates identity, applies CORS and rate
limiting, and routes to services through Eureka (`lb://<service-name>`).

### Route table

| Path pattern | Target | Auth |
|---|---|---|
| `/api/v1/auth/**` | `lb://auth-service` | Public |
| `/api/v1/users/**` | `lb://auth-service` | JWT |
| `/api/v1/admin/users/**` | `lb://auth-service` | ADMIN |
| `/api/v1/admin/products/**`, `/admin/categories/**`, `/admin/brands/**` | `lb://product-service` | ADMIN |
| `/api/v1/products/**`, `/categories/**`, `/brands/**` | `lb://product-service` | Public |
| `/api/v1/admin/inventory/**` | `lb://inventory-service` | ADMIN |
| `/api/v1/inventory/**` | `lb://inventory-service` | Public |
| `/api/v1/cart/**` | `lb://cart-service` | JWT |
| `/api/v1/admin/orders/**` | `lb://order-service` | ADMIN |
| `/api/v1/orders/**` | `lb://order-service` | JWT |
| `/api/v1/admin/payments/**` | `lb://payment-service` | ADMIN |
| `/api/v1/payments/**` | `lb://payment-service` | JWT |
| `/api/v1/admin/notifications/**` | `lb://notification-service` | ADMIN |
| `/api/v1/internal/**` | — | **not routed** (404) |

### Headers

| Header | Direction | Meaning |
|---|---|---|
| `Authorization: Bearer <token>` | in | Required on `JWT`/`ADMIN` routes |
| `X-User-Id`, `X-User-Email`, `X-User-Roles` | out | Set from the token claims; **any inbound value is stripped** |
| `X-Correlation-Id` | in/out | Honoured if supplied, otherwise generated; echoed in the response |
| `Retry-After` | out | Seconds to wait, on `429` |

### Behaviour

| Situation | Result |
|---|---|
| Missing / malformed / expired / foreign-signed token | `401 UNAUTHORIZED` |
| Valid token, non-ADMIN role on an ADMIN route | `403 FORBIDDEN` |
| No route matches | `404 ROUTE_NOT_FOUND` |
| Downstream service down or timed out | `503 SERVICE_UNAVAILABLE` |
| More than 5 requests/min per IP on a credential endpoint | `429 RATE_LIMIT_EXCEEDED` |
| Pre-flight from an origin other than the Angular app | `403` |

Credential endpoints rate limited per IP: `/api/v1/auth/login`, `/register`,
`/forgot-password`, `/reset-password`.

### Observability

| Endpoint | Description |
|---|---|
| `GET /actuator/health` | Gateway health |
| `GET /actuator/gateway/routes` | Active route table (read-only) |
| `GET http://localhost:8761/` | Eureka dashboard — shows gateway + all registered services |

## Auth / User Service (`:8081`)

Auth endpoints are public unless marked **JWT**. Errors use the `ApiResponse` envelope
(`success=false, message, data`).

### Auth

| Method | Path | Auth | Description |
|---|---|---|---|
| POST | `/api/v1/auth/register` | Public | Create a CUSTOMER. Body: `firstName`, `lastName`, `email`, `phone`, `password` → `201` |
| POST | `/api/v1/auth/login` | Public | Body: `email`, `password` → `{accessToken, refreshToken, tokenType, expiresIn, user}` |
| POST | `/api/v1/auth/refresh` | Public | Body: `{refreshToken}` → new pair (rotates the token) |
| POST | `/api/v1/auth/logout` | JWT | Body: `{refreshToken}` → revokes it |
| POST | `/api/v1/auth/forgot-password` | Public | Body: `{email}` → always `200` (never reveals whether the email exists) |
| POST | `/api/v1/auth/reset-password` | Public | Body: `{token, newPassword}` |

**Password policy** (spec 7.4): 8–100 chars with at least one uppercase, one lowercase, one
digit and one special character. Violations → `400` with a `field → message` map under `data`.

**Login response**

```json
{
  "success": true,
  "message": "Login Successful",
  "data": {
    "accessToken": "eyJhbGciOiJIUzM4NCJ9...",
    "refreshToken": "CrRuW9PtPoB--VBIPgbMaut...",
    "tokenType": "Bearer",
    "expiresIn": 900,
    "user": {
      "id": 1, "firstName": "Jay", "lastName": "Pal",
      "email": "jay@example.com", "phone": "+919876543210",
      "enabled": true, "emailVerified": false, "roles": ["CUSTOMER"]
    }
  }
}
```

**Access-token claims**: `sub` (userId), `email`, `roles`, `jti`, `iss`, `iat`, `exp`
(TTL 15 min; refresh token 7 days).

**Security behaviours**
- Email is unique **case-insensitively**; a duplicate → `409`.
- Wrong credentials → `401` `"Invalid email or password"` (never reveals whether the email exists).
- 5 consecutive failures lock the account for 15 min → `423 Locked`.
- A disabled account → `403`.
- Refresh tokens are stored **hashed** and rotated on every use. Reusing an already-revoked
  token revokes **all** of that user's tokens → `401`.
- Changing or resetting the password revokes all refresh tokens.

| Method | Path | Description |
|---|---|---|
| GET | `/api/v1/users/me` | Own profile |
| PUT | `/api/v1/users/me` | Update `firstName`, `lastName`, `phone` |
| PUT | `/api/v1/users/me/password` | Body: `{currentPassword, newPassword}`; wrong current → `422` |

| GET | `/api/v1/users/me/addresses` | List (default first) |
| GET | `/api/v1/users/me/addresses/{id}` | Single |
| PUT | `/api/v1/users/me/addresses/{id}` | Update |
| DELETE | `/api/v1/users/me/addresses/{id}` | Delete → `204` |

## Inventory Service (`:8083`)

Stock source of truth (spec §9). One counter row per product; reservations move units between
`available` and `reserved`; every change is written to an append-only `stock_movements` trail.

### Public — Availability

| Method | Path | Auth | Description |
|---|---|---|---|
| GET | `/api/v1/inventory/{productId}` | Public | `{productId, inStock, availableQuantity}` |

`availableQuantity` is capped at `metashop.inventory.display-quantity-cap` (default `10`), so the
storefront can render "only 3 left" without leaking exact stock levels. Unknown product → `404`.

```json
{ "productId": 50, "inStock": true, "availableQuantity": 3 }
```

### Admin — Stock management

| Method | Path | Auth | Description |
|---|---|---|---|
| POST | `/api/v1/admin/inventory` | ADMIN | Create the stock row → `201` + `Location` |
| GET | `/api/v1/admin/inventory/{productId}` | ADMIN | Full row incl. `reservedQuantity`, `lowStockThreshold` |
| PUT | `/api/v1/admin/inventory/{productId}` | ADMIN | Set or adjust the quantity |
| GET | `/api/v1/admin/inventory/low-stock` | ADMIN | Products at or below their threshold (paged) |

`POST` body — `lowStockThreshold` is optional (defaults to `5`):

```json
{ "productId": 50, "sku": "SKU-1049", "quantity": 25, "lowStockThreshold": 5 }
```

`PUT` body — supply **exactly one** of `quantity` (absolute) or `adjustment` (signed delta);
`lowStockThreshold` is optional. Supplying both, or neither, is a `400`. An `adjustment` that would
take available stock below zero is a `422`.

```json
{ "adjustment": -3 }
```

Response (`GET`/`PUT`, and the `POST` body):

```json
{
  "productId": 50, "sku": "SKU-1049",
  "availableQuantity": 22, "reservedQuantity": 1,
  "lowStockThreshold": 5, "lowStock": false, "inStock": true,
  "updatedAt": "2026-10-23T11:15:02.894"
}
```

`low-stock` uses the same paged envelope as the product list:
`{content, page, size, totalElements, totalPages, last}`. Add `?threshold=3` to ignore the
per-product thresholds.

### Internal (service-to-service)

> Not routed by the Gateway (404 from the outside). Every call must carry
> `X-Internal-Token: <metashop.internal.token>` — a missing or wrong value is `403`. Responses are
> plain JSON, **not** the `ApiResponse` envelope, so Feign clients stay trivial (D-022).

| Method | Path | Description |
|---|---|---|
| POST | `/api/v1/internal/inventory/reserve` | Hold stock for an order, all-or-nothing |
| POST | `/api/v1/internal/inventory/release` | Return the holds of an order to available stock |
| POST | `/api/v1/internal/inventory/confirm` | Turn the holds of an order into sales |
| POST | `/api/v1/internal/inventory/availability` | Bulk availability check with exact quantities |

`reserve` — duplicate `productId`s are merged; lines are applied in ascending `productId` order:

```json
{ "orderId": 500, "items": [ { "productId": 50, "quantity": 2 } ] }
```

`release` / `confirm`:

```json
{ "orderId": 500 }
```

All three are **idempotent per `orderId`** — a retried call returns the existing reservations rather
than holding or returning stock twice. Response:

```json
{
  "orderId": 500,
  "status": "RESERVED",
  "items": [ { "productId": 50, "quantity": 2, "status": "RESERVED",
               "expiresAt": "2026-10-23T11:15:08.057" } ]
}
```

`status` is the single line status when all lines agree, otherwise `MIXED`.

When **any** line cannot be satisfied the whole reservation is refused with `409` and nothing is
held. `data` lists every offending line:

```json
{
  "success": false,
  "message": "Insufficient stock for 1 item(s)",
  "data": [ { "productId": 50, "requested": 5, "available": 2 } ]
}
```

`availability` — `quantity` is optional per line and defaults to `1`:

```json
{ "items": [ { "productId": 50, "quantity": 3 } ] }
```

```json
{
  "items": [ { "productId": 50, "sku": "SKU-1049", "available": 10,
               "requested": 3, "sufficient": true, "inStock": true } ],
  "allAvailable": true
}
```

Internal callers see the **exact** quantity, unlike the capped public endpoint.

### Reservation lifecycle

| Status | Set when | Counters |
|---|---|---|
| `RESERVED` | `reserve` | `available −n`, `reserved +n` |
| `CONFIRMED` | `confirm` (payment succeeded) | `reserved −n` |
| `RELEASED` | `release` (payment failed / cancelled) | `available +n`, `reserved −n` |
| `EXPIRED` | expiry sweeper (TTL, default 15 min) | `available +n`, `reserved −n` |

`release` on a `CONFIRMED` order, and `confirm` on a `RELEASED`/`EXPIRED` order, are `422`.

### Concurrency

`reserve` uses a single conditional `UPDATE ... WHERE available_quantity >= :quantity`; the loser of
a race updates zero rows and gets `409`. See D-052 and
`src/test/java/com/shopMeta/inventory_service/concurrency/ReservationConcurrencyTest.java`.

## Cart Service (`:8084`)

One cart per user, owned by the JWT subject. The cart stores only `productId` + `quantity` +
the price at add time; **name, image, live price and stock are fetched on every read** from
product-service and inventory-service, so a line can never go stale in the database (spec 10.2).
All endpoints are JWT — there are no guest carts, because the platform has no anonymous identity yet.

### Endpoints

| Method | Path | Auth | Description |
|---|---|---|---|
| GET | `/api/v1/cart` | JWT | The caller's cart with live prices, line totals, subtotal and stock warnings. An empty cart is `200` with empty `items`, never `404`. |
| POST | `/api/v1/cart/items` | JWT | Add a product, or merge into an existing line. Body: `productId`, `quantity` (1..20). Validates product + stock first. |
| PUT | `/api/v1/cart/items/{itemId}` | JWT | Set a line to an absolute quantity (1..20). `itemId` is the line id from the cart response. |
| DELETE | `/api/v1/cart/items/{itemId}` | JWT | Remove one line → returns the updated cart. |
| DELETE | `/api/v1/cart` | JWT | Empty the cart (the cart row is kept, so the next add is cheap). Idempotent. |
| POST | `/api/v1/cart/validate` | JWT | Pre-checkout: is every line active, in stock and within limits? Always `200` — an invalid cart is an answer, not an error. |

### Cart response

```json
{
  "cartId": 3, "userId": 1,
  "items": [ {
    "itemId": 7, "productId": 50, "sku": "SKU-1049", "name": "Keyboard",
    "imageUrl": "/uploads/products/50.png",
    "unitPrice": 99.00, "addedPrice": 89.00, "priceChanged": true,
    "quantity": 2, "lineTotal": 198.00,
    "availableQuantity": 25, "inStock": true, "sufficient": true,
    "productActive": true, "warning": null
  } ],
  "totalItems": 2, "distinctItems": 1, "subtotal": 198.00, "currency": "INR",
  "hasWarnings": false, "warnings": [],
  "updatedAt": "2026-10-23T13:05:00"
}
```

- `unitPrice` / `lineTotal` / `subtotal` are **live** — an estimate of what the cart costs now, not a
  quote. The authoritative amount is the order snapshot.
- `priceChanged` + `addedPrice` let the UI flag "price changed since you added this".
- `warning` explains why a line cannot be ordered right now (inactive, out of stock, "only N left",
  over the quantity limit). Lines are **flagged, not silently dropped**.
- `itemId` (not `productId`) is what `PUT` / `DELETE /items/{id}` use.

### Validation rules

| Situation | Status |
|---|---|
| Unknown `productId` | `404` |
| Product deactivated / deleted in the catalogue | `422` |
| More than 20 units of one product (`metashop.cart.max-quantity-per-item`) | `422` |
| More than 50 distinct products (`metashop.cart.max-distinct-items`) | `422` |
| Not enough stock for the resulting quantity | `409` with `data: {productId, available}` |
| product-service / inventory-service unreachable or breaker open | `503` — the cart refuses rather than render stale prices |
| Another user's `itemId` | `404` (indistinguishable from a missing line — ids are never leaked) |

Mutations validate the product and the stock of the **resulting** quantity before writing, so the
cart can never hold a line that is already impossible to order. The cart only *checks* stock —
**reserving** it is order-service's job at checkout; between two checkouts the same unit can still
be promised to someone else.

### Internal (service-to-service)

| Method | Path | Auth | Description |
|---|---|---|---|
| DELETE | `/api/v1/internal/cart/{userId}` | `X-Internal-Token` | Clear a user's cart after their order was confirmed. Idempotent; plain `204`. |

Not routed by the Gateway (404 from the outside), same as the other internal APIs.

### Concurrency

The unique key on `(cart_id, product_id)` makes a concurrent double-add safe: the losing insert
fails and the caller retries once onto the update path. The `carts` row carries a `@Version`
column, so two racing mutations make the loser fail with a retryable `409` instead of silently
losing a line.

## Order Service (`:8085`)

Checkout and the order lifecycle (spec 11). An order is created **from the caller's cart** — there
is no way to pass order lines in the body. Prices, sku/name/image and the shipping address are
**frozen as snapshots at checkout** (spec 10.2): the order is the receipt and never moves when the
catalogue or the address book changes afterwards.

### Endpoints

| Method | Path | Auth | Description |
|---|---|---|---|
| POST | `/api/v1/orders` | JWT | Checkout: body `{ "shippingAddressId": 9 }`. Builds the order from the caller's cart, freezes the money + address snapshots, reserves stock, returns `201` with the order in `CREATED`. |
| GET | `/api/v1/orders` | JWT | The caller's orders, paged, newest first. |
| GET | `/api/v1/orders/{id}` | JWT | One order. Owner or admin — anyone else gets the same `404` as a missing order. |
| POST | `/api/v1/orders/{id}/cancel` | JWT | Owner cancels while `CREATED` (unpaid); the stock holds are released. |
| GET | `/api/v1/admin/orders` | ADMIN | Every user's orders, paged, optional `?status=` filter. |
| POST | `/api/v1/admin/orders/{id}/status` | ADMIN | Fulfilment: body `{ "status": "SHIPPED" \| "DELIVERED" \| "CANCELLED" }`. |

### Order response

```json
{
  "id": 100, "userId": 1,
  "status": "CREATED", "paymentStatus": "PENDING",
  "items": [ {
    "id": 1, "productId": 50, "sku": "SKU-1049", "name": "Keyboard",
    "imageUrl": "/uploads/products/50.png",
    "unitPrice": 99.00, "quantity": 2, "lineTotal": 198.00
  } ],
  "subtotal": 398.00, "shippingFee": 49.00, "total": 447.00,
  "shippingAddress": {
    "fullName": "Jay Pal", "phone": "9876543210",
    "line1": "12 Palm Road", "line2": "Near Park",
    "city": "Surat", "state": "Gujarat", "postalCode": "395007", "country": "IN"
  },
  "createdAt": "2026-10-23T15:20:00", "updatedAt": "2026-10-23T15:20:00"
}
```

- `subtotal` = Σ `unitPrice × quantity` at checkout prices; `shippingFee` is flat
  (`metashop.order.shipping-fee`, 49) and waived once the subtotal reaches
  `metashop.order.free-shipping-threshold` (499); `total = subtotal + shippingFee`.
- `items` carry the **frozen** product snapshot — a later price change never moves an order.
- `shippingAddress` is a **snapshot** copied from auth-service's internal API at checkout.

### Checkout flow (a saga, with compensation)

1. Read the buyer's cart **through the buyer's own forwarded JWT** (D-061 — there is no internal
   cart read) and run cart-service's pre-checkout validation. Empty cart → `422`; invalid cart →
   `409` with the issues.
2. Fetch the product snapshot for every line from product-service's internal batch API. A product
   that vanished or was deactivated between the two calls → `422` (catalogue drift).
3. Snapshot the shipping address from auth-service's internal API — a foreign address id is the
   same `404` as a missing one.
4. Persist the order as `CREATED` with the frozen money snapshot.
5. Reserve stock via inventory-service's internal API, **idempotent per `orderId`** (D-053).
   Out of stock → `409` with the unavailable lines, and the just-created order row is compensated
   to `CANCELLED`. A downstream outage → `503`, same compensation.

No Feign call runs inside a database transaction (D-062's rule, applied): the reads happen first,
then one short write, then the reservation.

### Status lifecycle

```
CREATED ──(payment succeeded, internal)──▶ CONFIRMED ──(admin)──▶ SHIPPED ──(admin)──▶ DELIVERED
   │──(payment failed / owner cancel)──▶ CANCELLED
```

- `CONFIRMED` is **payment's job** (payment-service, next phase, via the internal callbacks) — an
  admin cannot set it.
- `CANCELLED` and `DELIVERED` are terminal. Anything illegal is a `422`.
- A `CONFIRMED` (paid) order cannot be cancelled here — its stock is already sold and the refund
  flow arrives with payment-service.

### Internal (service-to-service) — for payment-service

| Method | Path | Auth | Description |
|---|---|---|---|
| POST | `/api/v1/internal/orders/{id}/payment-confirmed` | `X-Internal-Token` | `CREATED → CONFIRMED`, payment `PAID`, stock holds confirmed (become sales), buyer's cart cleared. Idempotent replay returns the confirmed order. |
| POST | `/api/v1/internal/orders/{id}/payment-failed` | `X-Internal-Token` | `CREATED → CANCELLED`, payment `FAILED`, stock holds released. Idempotent replay. |

Responses are plain JSON (no envelope, D-022). Not routed by the Gateway. An expired reservation
(stock TTL ran out during payment) is reported back as a `422` — a real conflict payment-service
must surface, not swallow.

### Concurrency

The `orders` row carries a `@Version` column: a racing payment callback and an admin update make
the loser fail with a retryable `409` instead of double-transitioning — and because the payment
callbacks are idempotent, the retry lands on the replay branch.

## Payment Service (`:8086`)

The payment ledger. The customer pays for an order through the mock gateway; the amount is read
from order-service's authoritative internal API (never from the request), and the outcome is
reported back through order-service's `payment-confirmed` / `payment-failed` callbacks (D-071),
which confirm or release the reserved stock. One row per **attempt**: a decline stays in the
ledger as `FAILED` and the retry is a new row (D-075).

- Gateway behaviour: `metashop.payment.gateway-mode` = `SUCCESS` (default) | `FAILURE` (demo the
  release path) | `RANDOM`. A real gateway replaces only the `MockPaymentGateway` bean.

### Customer (JWT)

| Method | Path | Description |
|---|---|---|
| POST | `/api/v1/payments` | Pay for an order — body `{ "orderId": 100, "method": "CARD" }` (`CARD`/`UPI`/`WALLET`). `201` when captured (`order → CONFIRMED`, stock sold, cart cleared); `200` + `success=false` when declined (`order → CANCELLED`, stock released, the `FAILED` attempt in `data`). |
| GET | `/api/v1/payments` | Your payment attempts, paged, newest first. |
| GET | `/api/v1/payments/{id}` | One attempt — owner or admin; a customer asking for someone else's gets the same `404` as a missing one. |

Example — captured:

```json
{
  "success": true,
  "message": "Payment captured; the order is confirmed",
  "data": {
    "id": 1, "orderId": 3, "userId": 2,
    "amount": 7712.00, "method": "CARD", "status": "SUCCEEDED",
    "gatewayReference": "MOCK-3-9f2c1a8b", "failureReason": null,
    "createdAt": "...", "updatedAt": "..."
  }
}
```

Example — declined (`200`, the attempt is a recorded fact, its outcome is data):

```json
{
  "success": false,
  "message": "Declined by the mock gateway",
  "data": { "id": 2, "orderId": 4, "status": "FAILED", "failureReason": "Declined by the mock gateway", "...": "..." }
}
```

### Admin (ADMIN)

| Method | Path | Description |
|---|---|---|
| GET | `/api/v1/admin/payments` | The whole ledger, paged; filter by `?status=` or `?orderId=` (order wins when both are given). |

### Payment states

| State | Meaning |
|---|---|
| `PENDING` | The charge is being taken (an interrupted attempt is visible in the ledger). |
| `SUCCEEDED` | Gateway captured **and** order-service confirmed the order. |
| `FAILED` | Declined by the gateway, or the capture could not be applied (order refused the confirmation). The customer may retry — a new row. |

### Honesty rules (D-077)

- Captured but order-service **refuses** (`422`, e.g. the reservation expired): the row becomes
  `FAILED` with the reason and the caller gets the `422` — never a quiet decline while the money
  was taken.
- Captured but order-service is **unreachable**: the row stays `SUCCEEDED` (the money is real) and
  the caller gets the `503`. A reconciliation sweep is future work.
- Declined but the failure report cannot be delivered: the row stays `FAILED` and the decline is
  still returned — the order side reconciles through its reservation TTL / the owner's cancel.

### Internal (service-to-service)

| Method | Path | Auth | Description |
|---|---|---|---|
| GET | `/api/v1/internal/orders/{id}` (on **order-service**) | `X-Internal-Token` | The authoritative order read payment-service takes the amount and the ownership/status checks from (D-076). |

payment-service's own internal endpoints: none yet — refund flows / a notification consumer would
add them when the consumer exists.

## Notification Service (`:8087`)

The event consumer and email sender (spec §13). It has **no outbound HTTP calls** — it is driven
entirely by Kafka and its only HTTP surface is the admin log below. An event arrives, is mapped to
one of ten Thymeleaf templates, rendered, recorded in `notifications`, and sent through Spring Mail
(Mailpit in dev). Kafka delivers at least once, so every event is de-duplicated by `event_id` before
anything is sent (D-080, D-082).

### Admin (ADMIN)

| Method | Path | Description |
|---|---|---|
| GET | `/api/v1/admin/notifications` | The audit log, paged, newest first. `?status=PENDING\|SENT\|FAILED`, `?page=`, `?size=` (max 100). The rendered `body` is **omitted** — fetch one notification for that. |
| GET | `/api/v1/admin/notifications/{id}` | One notification **including** the rendered HTML `body`, so an admin can answer "what did the customer actually receive?". |
| POST | `/api/v1/admin/notifications/{id}/retry` | Re-sends the stored subject and body through SMTP once. `422` if the notification is already `SENT` (that would duplicate the email); `503` if the mail server refuses again, leaving the row `FAILED` with the new reason. |

Example — the list (`data` is the page, no envelope on success):

```json
{
  "content": [
    {
      "id": 9, "eventId": "9f1c…", "userId": 7,
      "email": "asha@example.com", "type": "ORDER_CONFIRMED",
      "subject": "Order MS-000042 confirmed", "status": "SENT",
      "retryCount": 0, "error": null,
      "createdAt": "2026-10-25T11:50:03", "sentAt": "2026-10-25T11:50:03"
    }
  ],
  "page": 0, "size": 20, "totalElements": 10, "totalPages": 1, "last": true
}
```

Example — retry refused because the email already went out:

```json
{ "success": false, "message": "Notification 9 was already sent and cannot be retried" }
```

### Notification states

| State | Meaning |
|---|---|
| `PENDING` | The row exists and the send is in flight (or a crash interrupted it — the row is the evidence). |
| `SENT` | Delivered to the SMTP server, and the event was recorded in `processed_events`. |
| `FAILED` | The last attempt was refused. `retryCount` counts the attempts, `error` holds the reason. This is the admin's retry queue. |

### Consumed events → emails (spec §14)

Topics: `user.events`, `order.events`, `payment.events`, `inventory.events` (the whole topic, not a
filtered subset — an event type with no email is a logged skip, not a failure).

| Event | Notification type | Template |
|---|---|---|
| `UserRegisteredEvent` | `WELCOME` | `welcome` |
| `PasswordResetRequestedEvent` | `PASSWORD_RESET` | `password-reset` |
| `OrderConfirmedEvent` | `ORDER_CONFIRMED` | `order-confirmed` (line items + shipping address) |
| `OrderShippedEvent` | `ORDER_SHIPPED` | `order-shipped` |
| `OrderDeliveredEvent` | `ORDER_DELIVERED` | `order-delivered` |
| `OrderCancelledEvent` | `ORDER_CANCELLED` | `order-cancelled` |
| `PaymentSuccessEvent` | `PAYMENT_SUCCESS` | `payment-success` (receipt) |
| `PaymentFailedEvent` | `PAYMENT_FAILED` | `payment-failed` |
| `PaymentRefundedEvent` | `PAYMENT_REFUNDED` | `payment-refunded` |
| `InventoryLowEvent` | `LOW_STOCK` | `low-stock` → the **admin** address (no owning user) |

### Failure handling (D-082)

- A **delivery** failure is recorded as `FAILED` and rethrown. `DefaultErrorHandler` retries the
  record three times with exponential backoff (1s / 2s / 4s), then `DeadLetterPublishingRecoverer`
  publishes it to `<source-topic>.DLT` and the offset is committed.
- A payload that does not fit its event type, or a record that cannot be parsed at all, is
  **not retried** — it fails identically every time — and goes straight to `<source-topic>.DLT`.
  Both deserializers are wrapped in `ErrorHandlingDeserializer`; without it a single unparseable
  record makes the container throw on every poll and stall the whole listener for ever.
- The offset is committed **only** after the notification is `SENT` (manual acks, spec §14.4).

### Internal (service-to-service)

None. This service exposes no internal HTTP surface and calls no other service (D-080).

### Not yet implemented

Nothing in the other services publishes to Kafka yet, so the event catalogue above is defined but
not produced — see README. The three payment events also carry no email address in the spec's
payload; they now accept an optional `email` field, and an event without one is skipped rather than
dead-lettered (D-081).
